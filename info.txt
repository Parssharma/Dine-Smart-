1. EXECUTIVE SUMMARY & OBJECTIVE
--------------------------------------------------------------------------------
DineSmart bridges high-performance low-level Data Structures & Algorithms (DSA)
in C++ with modern web application engineering (Node.js/Express, MongoDB, 
React + Vite).

It solves operational bottlenecks in high-volume dining environments:
- Real-time table searching, ranking, and AI recommendations
- Large party multi-table combinations via Backtracking optimization
- Live restaurant floor operations & dynamic occupancy tracking
- FIFO digital queue/waitlist with automated promotion
- Complete reservation lifecycle state machines with append-only audit trail
- Business Intelligence & Operational Analytics with CSV export
- Strict Role-Based Access Control (RBAC) and JWT Authentication
- Clean architectural separation between Customer & Management Portals

2. SYSTEM ARCHITECTURE & TECH STACK
--------------------------------------------------------------------------------

[1] FRONTEND (React 19 + Vite 8)
    - Architecture: Route-based Multi-Portal Architecture (React Router)
    - Customer Application: /, /reserve, /reservations
    - Management Application: /management/login, /management, /management/*
    - Styling: Vanilla CSS with custom HSL/dark theme tokens, glassmorphism, responsive design
    - Icons: lucide-react

[2] BACKEND (Node.js + Express + Mongoose)
    - Framework: Express.js REST API
    - Database: MongoDB via Mongoose ODM
    - Authentication: Stateless JWT + Bcrypt password hashing
    - Authorization: Role-Based Access Control (CUSTOMER vs MANAGER)
    - Concurrency Control: Asynchronous global mutex locks for atomic table operations
    - IPC: Child process stdio JSON streaming with 5000ms timeout safeguards

[3] DSA ENGINE (C++17 Standalone Subprocess)
    - Priority Queue / Max-Heap: Multi-factor scoring for optimal table recommendations
    - Backtracking Combiner: Optimal subset-sum table combinations for large parties
    - Custom HashMap: Quadratic probing & polynomial string hashing for O(1) table lookup
    - FIFO Queue: Arrival-based waitlist sequencing

--------------------------------------------------------------------------------
3. DETAILED C++ DSA ENGINE SPECIFICATIONS
--------------------------------------------------------------------------------

File Path: dsa-engine/src/
Executable: dsa-engine/engine.exe

[A] Backtracking Algorithm (dsa-engine/src/Backtracking.hpp)
    - Purpose: Finds optimal combinations of available tables for large groups (>= 6).
    - Goal: Accommodate party size while strictly MINIMIZING unused seat capacity.
    - Complexity: O(2^N) search space with aggressive branch pruning.
    - Output: Array of selected table IDs and total combined capacity.

[B] Priority Queue / Max-Heap (dsa-engine/src/PriorityQueue.hpp)
    - Purpose: Real-time table recommendation ranking.
    - Multi-Factor Scoring Formula:
        Score = (CapacityFit * 10) + (LocationMatch * 5) + (Rating * 2)
        - CapacityFit = 10 if table.capacity == partySize else max(1, 10 - (table.capacity - partySize))
        - LocationMatch = 1 if table.location == preference else 0
        - Rating = table.rating (1.0 to 5.0)
    - Complexity: O(N log K) to return top-ranked recommendations.

[C] Custom HashMap (dsa-engine/src/HashMap.hpp)
    - Purpose: O(1) in-memory table lookup by ID.
    - Implementation: Polynomial rolling string hash with Quadratic Probing collision resolution.

[D] FIFO Queue (dsa-engine/src/Queue.hpp)
    - Purpose: First-In, First-Out queue ordering for waitlisted diners.
    - Implementation: Custom linked queue preserving strict arrival timestamps.

5. SECURITY, AUTHENTICATION & RBAC MODEL
--------------------------------------------------------------------------------

- Passwords hashed using bcrypt (10 rounds).
- Passwords and password hashes are strictly stripped from all API outputs.
- JWT tokens signed with HMAC-SHA256 containing userId and role.
- Role Hierarchy:
    * CUSTOMER : Can book tables, view own bookings/history, join waitlist, cancel own.
    * MANAGER  : Full access to operational dashboard, floor plan, table CRUD, 
                 lifecycle state changes (Check-in, Seat, Complete, No-Show), 
                 waitlist promotions, analytics, and audit trail.

6. BOOKING LIFECYCLE & AUDIT STATE MACHINE
--------------------------------------------------------------------------------

Lifecycle States:
  Confirmed ──> Checked In ──> Seated ──> Completed
      │                            │
      ├──> Cancelled               └──> Cancelled
      └──> No Show

Key Rules:
1. Double-Booking Prevention: Atomic conflict check prevents overlapping time slots 
   on the same table for identical dates.
2. Advance vs Live Occupancy: Advance bookings mark table status as RESERVED without 
   forcing physical table isOccupied=true until live time slot arrives.
3. Append-Only Audit Trail: Every state transition logs:
   - previousStatus, newStatus, timestamp, changedBy (User ID), changedByName, 
     changedByRole, and optional reason/notes.
4. Auto-Notification Dispatch: Triggers notification records for customer and manager 
   upon confirmations, cancellations, check-in, and waitlist movements.

10. HOW TO RUN & DEVELOP
--------------------------------------------------------------------------------

[1] Prerequisites:
    - Node.js (v18+)
    - MongoDB running on mongodb://localhost:27017/smart-booking
    - g++ compiler (for C++ engine compilation if rebuilding)

[2] Compile C++ Engine:
    cd dsa-engine
    g++ -std=c++17 src/main.cpp -o engine.exe

[3] Start Backend:
    cd backend
    npm install
    npm run dev          (Runs on http://localhost:5000)

[4] Start Frontend:
    cd frontend
    npm install
    npm run dev          (Runs on http://localhost:5173)

[5] Run Tests:
    cd backend
    npm test
